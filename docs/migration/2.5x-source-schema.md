# 2.5.x source schema reference

Table-by-table reference for the Wiki.js 2.5.x database schema, produced for the source-connector /
schema-mapping spike (Feature 412). This is what a migration importer — whether reading a live
Postgres source directly, or unpacking an export bundle from MySQL/MariaDB/MSSQL/SQLite — actually
has to map onto Wiki.js 3.0's schema.

## Read this first: the two things that matter most for the spike

**1. Everything is an auto-increment integer primary key, not a UUID** — with three exceptions
worth knowing by name:

- `assetData.id` and `pageTree.id` are `integer` primary keys **without** `.increments()`: they are
  manually assigned by the application to equal `assets.id` / `pages.id` respectively (a 1:1
  "detail table" split, not an independent identity space).
- `navigation`, `settings`, `authentication`, `storage` (and, out of scope here, `analytics`,
  `editors`, `locales`, `loggers`, `renderers`, `searchEngines`, `commentProviders`) are singleton
  config tables keyed by a `string` `key`, not an integer at all.

Either way, **every legacy primary key must be remapped to a fresh UUID on import**, and every FK
column that carries an old integer (or string key) must be rewritten to point at the new UUID. A
source connector needs an old-id → new-UUID lookup table per entity during the whole import run.

**2. Column _type_ varies by source DB engine on four columns**, and only on a live-Postgres source
connection can this be ignored (Postgres was always `TEXT`/`bytea` here) — the export-bundle path
(MySQL/MariaDB/MSSQL/SQLite) must special-case each:

| Column                | postgres / sqlite         | mysql / mariadb                                                | mssql                                   |
| --------------------- | ------------------------- | -------------------------------------------------------------- | --------------------------------------- |
| `pages.content`       | `TEXT`                    | `LONGTEXT`                                                     | `VARCHAR(max)`                          |
| `pages.render`        | `TEXT`                    | `LONGTEXT`                                                     | `VARCHAR(max)`                          |
| `pageHistory.content` | `TEXT`                    | `LONGTEXT` (altered in `2.1.85.js`, not present at `2.0.0.js`) | `VARCHAR(max)` (altered in `2.1.85.js`) |
| `assetData.data`      | `bytea` (knex `binary()`) | `LONGBLOB`                                                     | knex `binary()` (`VARBINARY(max)`)      |

`pages.content`/`render` got the per-engine type in the original `2.0.0.js` `CREATE TABLE`;
`pageHistory.content` started as a plain `text()` in `2.0.0.js` and only got the same treatment via
an `ALTER TABLE` in `2.1.85.js` — so a source reading `2.0.0.js` alone would under-provision the
MySQL/MSSQL column size for `pageHistory.content`. There's also a related **table-level** (not
column-type) variance: every table gets `.charset('utf8mb4')` on mysql/mariadb only — irrelevant to
Postgres-direct but worth setting explicitly when the bundle path re-creates tables on a MySQL
target.

Two more nullability quirks fall out of that same `mysql`-is-different pattern: `pages.extra` and
`pageHistory.extra` (added in `2.4.13.js`) are `NOT NULL DEFAULT '{}'` everywhere **except** MySQL,
where the migration leaves them nullable with no default — a source-bundle reader must not assume
`extra` is always present on a MySQL-origin export.

## Legend

- **Nullable** reflects `.notNullable()` presence; a blank default means no `.defaultTo()` was set
  (value is genuinely nullable/absent, not empty-string).
- Every `createdAt`/`updatedAt`/`publishStartDate`/etc. timestamp in this schema is stored as a
  **plain `string`** column (ISO-formatted by the application), not a native `timestamp`/`date`
  type — parse, don't cast.
- "FK (unenforced)" means the column is semantically a foreign key but the migration never calls
  `.references()`/`.inTable()` on it — there is no DB-level constraint, only an application-level
  convention.

`versionDate` is not simply "when this row was created" (that's `createdAt`) — the `2.2.17.js`
migration backfills it, per source engine, with the **previous** revision's `createdAt` for the same
`pageId` (falling back to this row's own `createdAt` if there is no previous row). A source connector
reproducing this semantic must replicate that self-join, not just copy the column value verbatim if
recomputing history for any reason; for a straight migration, copying the stored value is correct
and simpler.

`apiKeys` (added `2.2.3.js`) and `commentProviders` (added `2.4.14.js`) are new tables introduced by
the spot-checked migrations but are not in this task's target table list, so they are not documented
here beyond this note.

## Implications for the spike's two connector paths

- **Postgres-direct connection**: can ignore every row in the "column _type_ varies by source DB
  engine" table above — a live Postgres source was always `TEXT`/`bytea`. Still needs the UUID
  remapping pass (every PK is a legacy auto-increment integer or string key) and still needs to
  handle the `extra`-column mysql-nullability quirk as N/A (Postgres source is always the
  NOT-NULL-with-default variant).
- **Export-bundle path (MySQL/MariaDB/MSSQL/SQLite)**: must read the bundle's declared source engine
  and branch on it for `pages.content`/`render`, `pageHistory.content`, and `assetData.data` sizes/
  types, must tolerate `NULL` `extra` on a MySQL-origin bundle, and should not attempt to enforce
  `storage.mode` as a checked enum (the source schema never did either).
