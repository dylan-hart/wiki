# 2.5.x → 3.0 column-level mapping

The core deliverable of the source-connector / schema-mapping spike (Feature 412): one row per 2.x
column, stating its 3.0 destination (`table.column` in [`backend/db/schema.ts`](../../backend/db/schema.ts))
or an explicit **NO DESTINATION YET** marker. This is what any later importer feature (414/416/418/420)
codes its transform step against — it does not re-derive the mapping itself.

**Inputs**: [`2.5x-source-schema.md`](2.5x-source-schema.md) (Task 706 — the 2.x column inventory) and
[`2.5x-export-bundle-format.md`](2.5x-export-bundle-format.md) (Task 707) on the source side;
`backend/db/schema.ts` on the destination side, cross-checked against `backend/models/*.ts` wherever
the schema alone doesn't say how a column is actually populated (`pages.path` vs. `tree.folderPath`,
`users.auth`'s per-strategy shape, `assets.id`/`tree.id` sharing a primary key).

[`verify-mapping-doc.test.mjs`](verify-mapping-doc.test.mjs) enforces that every column documented in
`2.5x-source-schema.md`'s 18 table sections has a corresponding row below, and that the structural
transforms called out in the task description are stated explicitly — run
`node --test docs/migration/verify-mapping-doc.test.mjs` from the repo root.

## Read this first: five things that are not simple renames

1. **Every legacy integer/string PK becomes a fresh UUID.** Every table below carries this
   transform implicitly on its `id` (or `key`) column, so it is stated once here rather than
   repeated 18 times: an importer needs an old-id → new-UUID lookup table per 2.x entity for the
   whole run, exactly as `2.5x-source-schema.md`'s "Read this first" already establishes for the
   source side.
2. **Every 2.x row lands under one `siteId`.** 2.x has no multi-site concept at all — there is
   exactly one wiki per 2.x database. 3.0 makes `siteId` a required column on nearly every table
   (`pages`, `pageHistory`, `assets`, `tags`, `tree`, `navigation`, `blocks`, `storage`, …), so a
   straight 2.x → 3.0 import writes the _same_ target `siteId` (the one site created for this
   import) onto every single row it produces. There is no 2.x column this comes from — it is an
   import-time constant, not a mapped value.
3. **`assets` + `assetData` + `assetFolders` (three 2.x tables) collapse into one 3.0 `assets`
   row.** 3.0's `assets` table inlines the blob (`data`, `preview` — both `bytea`) directly rather
   than splitting it into a detail table the way 2.x's `assetData` did, and folder placement moves
   out of `assets` entirely into the unified `tree` table (see point 4) rather than staying as an
   `assetFolders` FK chain. `storageInfo` (jsonb) is new in 3.0 with no 2.x source at all — it
   records which storage-sync targets have a copy and is populated by the storage layer, not by an
   importer.
4. **2.x's two separate hierarchies (`pageTree`'s integer parent-pointer chain, `assetFolders`'
   own separate integer parent-pointer chain) both become paths in one 3.0 `tree` table**, keyed by
   `folderPath` (`ltree`) instead of a walked parent chain. A `tree` row's `id` is the _same_ UUID
   as the `pages.id` or `assets.id` it describes (confirmed in `backend/models/pages.ts`'s
   `addPage()`/`backend/models/assets.ts`'s asset-create path, both of which pass the just-inserted
   row's id straight into `tree.addPage`/`tree.addAsset`) — mirroring the exact shared-PK
   convention `2.5x-source-schema.md` already documents for 2.x's `pageTree.id = pages.id` /
   `assetData.id = assets.id`. Concretely: `pageTree.parent` (walk-the-chain) and `assetFolders.parentId`
   (a second, separate chain) both convert to one `tree.folderPath` ltree value per row; there is no
   column-to-column mapping for "parent" any more, only a recomputed materialized path.
5. **Per-module `config` blobs need key-by-key remapping, not a blind copy.** 2.x and 3.0 prop
   names inside `authentication.config` / `storage.config` are **not guaranteed to match** even for
   the same module `key`. Three modules were spot-checked directly against both engines'
   `definition.yml` (2.x fetched from `requarks/wiki` `server/modules/**/definition.yml` @ `main`;
   3.0 read from this repo's `backend/modules/**/definition.yml`) — see
   [Module config remapping](#module-config-remapping) below for the concrete mismatches found in
   each.

### Orphaned history — a `pageHistory` row whose 2.x `pageId` names no current page

`backend/migration/content-staging.ts` stages every `pageHistory` row it reads against the `pages`
rows it has also read for the same run. A row whose 2.x `pageId` matches none of them — almost always
a page the 2.x wiki itself had already deleted, so no live page exists for its history to attach to —
is collected separately as `orphanedHistory` rather than joined onto a `StagedPage.history` array.

**Decision: import these rows, against a synthesized `pageHistory.pageId`, rather than drop them.**
Mint one fresh UUID per distinct 2.x source page id (not one per history row) — every row that shares
a `sourcePageOldId` is one defunct page's revision chain and should stay grouped under the one
synthetic `pageHistory.pageId` the same way a live page's rows share its real one. Never `NULL`:
`pageHistory.pageId` is `uuid().notNull()` (`backend/db/schema.ts:983-985`), so a synthesized id is
the only column-legal way to carry the row at all, and the id is drawn fresh (not reused from any 2.x
old-id table) specifically so it cannot coincide with a real page's UUID.

**Reasoning.** `pageHistory.pageId` is deliberately not a foreign key "so history outlives a deleted
page" (`backend/db/schema.ts:983-985`, echoed in the `pageId` row of the table above) — orphaned rows
are exactly that scenario, just deleted before the migration ran rather than after it. Dropping them
would discard real audit trail — including, for a row whose `action` maps to 3.0's `deleted`, the one
copy of a page's content from the moment it was deleted — for no query-safety reason, once every
reader of `pageHistory` is checked against a row whose `pageId` matches no live page:

- **`getVersions`/`getVersion`** (`backend/models/pageHistory.ts:262-298`, `:399-454`) — both take an
  exact `pageId` a caller already holds from a live `pages` row. A synthesized id foreign to every real
  page never matches either query, so orphaned rows are correctly invisible here: there is no live page
  to browse "its" history for in the first place.
- **`listRecoverable`** (`backend/models/pageHistory.ts:466-520`) — the delete-recovery listing behind
  the admin "recover a deleted page" flow — matches on `(siteId, locale, path)` + `action = 'deleted'`
  + `NOT EXISTS` a live page at that address, and never reads `pageId` at all. This is precisely what
  orphaned history describes: a page 2.x had already deleted, with no 3.0 page at its address. Importing
  it means a page a 2.x author deleted becomes recoverable through 3.0's *existing* recovery UI with no
  new code, provided its `action` was mapped onto 3.0's `deleted` per the `action` row above — the
  outcome the non-FK `pageId` design was already built to allow.
- **`getDeletedVersion`** (`backend/models/pageHistory.ts:532-568`) — keyed on the history row's own
  `id` plus `action = 'deleted'`; `pageId` plays no part, so a synthesized value changes nothing.
- **`contributorCountsForGraph`** (`backend/models/pageHistory.ts:325-392`) — groups by `pageId` for
  the knowledge graph's edit-volume node sizing. Its only caller, `backend/api/graph.ts`, looks values
  up per *live* page id off `pages.listAllForGraph()`'s own rows and never iterates the map's keys, so
  the extra entries a synthesized pageId adds sit unused and touch no real page's count.

No reader path breaks on, or needs anything from, a synthesized `pageId` — so there is no case for
dropping the rows instead. Implementing this (minting the synthetic ids and extending
`backfillPageHistory` to insert `orphanedHistory` alongside each page's own history) is a separate
child of this task's parent epic.

## pageLinks

**NO DESTINATION YET.** 3.0's `backend/db/schema.ts` has no `pageLinks` table, no outbound-link index
table of any kind, and no equivalent model. This is easy to conflate with `pages.relations` (a jsonb
column that does exist on 3.0 `pages`) because the names are adjacent in meaning, but they are not the
same feature: `pages.relations` is a small, **user-curated** list of "related page" buttons a page
author explicitly adds (position/label/caption/icon — see `frontend/src/components/PageRelationDialog.vue`),
not an **automatically rebuilt index of every outbound link found in the page's content**, which is
what 2.x's `pageLinks` is (rebuilt from content on every save, per `2.5x-source-schema.md`). There is
currently nowhere for 2.x's `pageLinks` rows to land; an importer either drops them (they are a
derived index, regenerable from `pages.content` once a 3.0-side link-indexing feature exists) or holds
them pending that feature.

| `path`                 | **NO DESTINATION YET** | no target table   |
| `localeCode`           | **NO DESTINATION YET** | no target table   |
| `pageId`               | **NO DESTINATION YET** | no target table   |

**Re-run safety (Task 414/732):** the users/groups importer (`backend/migration/importers/users-groups.ts`)
detects a source `groups`/`users` row that was already imported by a prior run by matching on the
target's own natural key instead of a separately persisted old-id → new-UUID record — `name` for
`groups`, `email` for `users` (already unique). No extra id-mapping table or JSON artifact is
persisted: the matching target row's own primary key already supplies the id a persisted map would
have, so `importUserGroups()`'s translation works identically on a second run whether the id came from
a fresh insert or from this lookup. When a match is found, the row is never re-inserted; if the
freshly-converted candidate's content also matches what's stored, it's reported `existing`, otherwise
`diverged` — and a `diverged` row is deliberately **not** overwritten, to avoid silently discarding an
administrator's own in-3.0 edits to an already-imported group/user.

## Module config remapping

Per-module `config` blobs are not portable as-is: 2.x and 3.0 prop names for the _same_ module `key`
diverge, confirmed by diffing `definition.yml` for three modules directly.

### `local` authentication module

- 2.x: `server/modules/authentication/local/definition.yml` @ `requarks/wiki` `main` declares
  `props: {}` — **no configurable props at all**.
- 3.0: `backend/modules/authentication/local/definition.yml` declares three props: `enforceTfa`,
  `emailValidation`, `allowForgotPassword`.
- **Finding**: because 2.x's `config` for this module is always empty, there is nothing to remap
  key-by-key for `local` specifically — the three 3.0 props are new capabilities with no 2.x source
  and simply take their schema defaults on import. This module is the good case, not the general
  one; `git` and `s3` below show why the remap step cannot be skipped for every module just because
  it was a no-op here.

### `git` storage module

- 2.x: `server/modules/storage/git/definition.yml` @ `requarks/wiki` `main`.
- 3.0: `backend/modules/storage/git/definition.yml`.
- **Findings**:
  - `sshPrivateKeyMode`'s enum **values** were renamed, not just relabeled: 2.x uses
    `'path'`/`'contents'`; 3.0 uses `'path'`/`'inline'`. A 2.x `config.sshPrivateKeyMode: 'contents'`
    must be rewritten to `'inline'` on import, not copied verbatim, or the imported config silently
    fails validation against 3.0's `enum`.
  - `branch`'s default value changed from 2.x `'master'` to 3.0 `'main'` — only matters for a 2.x
    row that never had a `branch` set at all (relying on the default), since an explicit value
    copies straight across either way.
  - `alwaysNamespace` (2.x, boolean, "whether to put content from the primary language into a
    subfolder") has **no 3.0 prop with that name or an equivalent** in `backend/modules/storage/git/definition.yml`
    — **NO DESTINATION YET** for this specific config key, even though the module itself maps
    cleanly.
  - The remaining props (`authType`, `repoUrl`, `sshPrivateKeyPath`, `sshPrivateKeyContent`,
    `verifySSL`, `basicUsername`, `basicPassword`, `defaultEmail`, `defaultName`, `localRepoPath`,
    `gitBinaryPath`) keep identical names on both sides and copy straight across.

### `s3` storage module

- 2.x: `server/modules/storage/s3/definition.yml` @ `requarks/wiki` `main`.
- 3.0: `backend/modules/storage/s3/definition.yml`.
- **Findings** — this is the module with the largest real reshape:
  - 2.x has a single flat `region` string prop (free text, AWS-only — the module description itself
    says "Amazon S3", full stop). 3.0 splits this into a `mode` selector (`aws` / `do` /
    `custom`) plus **three** separate region-shaped props gated by `mode`: `awsRegion` (a
    constrained enum of real AWS region codes), `doRegion` (a DigitalOcean Spaces region enum), and
    `endpoint` (a free-text URI for `custom`). A 2.x row's `config.region` value maps to
    3.0 `config.awsRegion` **and** requires synthesizing `config.mode: 'aws'` explicitly, since 2.x
    never recorded a mode (2.x S3 support was implicitly AWS-only) and 3.0 has no default that
    infers it.
  - `bucket`, `accessKeyId`, `secretAccessKey` keep identical names and copy straight across.
  - `storageTier`, `sslEnabled`, `s3ForcePathStyle`, `s3BucketEndpoint` are **new in 3.0, no 2.x
    source** — none of these existed as configurable props in the 2.x module at all, so they take
    their `definition.yml` defaults (or are left unset, for the ones without one) on import.

## Summary: NO DESTINATION YET rows, by cause

Grouped here for anyone scoping the follow-up features (414/416/418/420) that will need to either
build the missing destination or explicitly decide to drop the field:

- **A whole 3.0 feature doesn't exist yet**: `pageLinks` (all columns — no link-index feature),
  `navigation.key` (no singleton-key concept).
- **The 3.0 feature exists but the migration's connector interface can't read it yet**: `comments`
  (all columns — the 3.0 comments table/model/API have shipped, but `SourceConnector` has no
  `comments()` generator to read 2.x comments through).
- **A 3.0 column was deliberately dropped as a product decision**, not merely unbuilt:
  `pageHistory.render` (documented in-schema as intentionally not stored), `pages.isPrivate` /
  `pages.privateNS` / `pageTree.isPrivate` / `pageTree.privateNS` (superseded by page-rule
  permissions), `pageTree.depth` / `pageTree.ancestors` (superseded by `ltree` operators),
  `storage.mode` (2.x's own value was likely a copy-paste bug per `2.5x-source-schema.md` and 3.0
  never modeled sync direction), `storage.syncInterval` (sync scheduling "not modelled yet" per the
  `git` module's own `definition.yml` comment).
- **Needs a follow-up spot-check, not yet audited here**: `pages.extra`, `pages.createdAt` (folds
  into a synthesized `pageHistory` row instead), `pageHistory.createdAt`, `pageHistory.hash`,
  `users.pictureUrl`, `users.localeCode`, `users.defaultEditor`, `tags.title`,
  `authentication.order`, every individual `settings.value` key (a full 2.x-setting-key vs.
  `base.yml`-key audit is out of this task's scope), and any `authentication`/`storage` module
  other than the three spot-checked above (`local`, `git`, `s3`) — each additional module (`google`,
  `github`, `oidc`, `disk`, `db`, `azure`, `gcs`, `sftp`) needs the same `definition.yml` diff before
  its `config` blob can be trusted to remap correctly.
