# 2.5.x → 3.0 field-level mapping: settings, authentication, storage

Feature 412's [`2.5x-to-3.0-mapping.md`](2.5x-to-3.0-mapping.md) covers the `settings` /
`authentication` / `storage` tables only at the **column** level (`key`, `value`, `updatedAt` for
`settings`; the eight `authentication` columns; the six `storage` columns), and says so explicitly:

> individual 2.x setting keys are not guaranteed to have the same name/shape as their 3.0
> equivalent … auditing every 2.x setting key against 3.0's is out of this task's scope … and
> should be a follow-up, not assumed complete here

This document **is** that follow-up. It enumerates every individual 2.5.x `settings.key` row (not
just the `key`/`value` columns that hold it), every `authentication` column, and every `storage`
column, each mapped to its precise 3.0 destination — a `sites.config` JSON path (per the default
shape in `backend/models/sites.ts:90-192`), a 3.0 `settings` table key (per
`backend/models/settings.ts:39-161`), an `authentication` table column, or a `storage` table
column/prop — or an explicit **NO DESTINATION** marker where none exists. It supersedes the
placeholder note quoted above; `2.5x-to-3.0-mapping.md` is not edited by this task (the task
description asks for a new spec document, and the column-level doc's own scope note already points
here).

## Method

2.x's `settings` table is a generic `(key, value, updatedAt)` store — the schema alone doesn't say
which keys exist or what shape each `value` takes (`2.5x-source-schema.md`'s `## settings` section
already flags this). That inventory has to come from the application code that reads/writes it, not
from `db/migrations/*.js`. Two kinds of source were used, both fetched 2026-08-17 from
`requarks/wiki` `main` and vendored under [`vendor/2x-settings/`](vendor/2x-settings/):

- **`server/app/data.yml`** — the `defaults.config` block `config.js`'s `init()` deep-merges under
  whatever `config.yml` supplies. This is authoritative for the *shape* of most keys, but a
  `data.yml` default is a **config.yml/in-memory default**, not proof the key was ever written to
  the `settings` **table** — only a `configSvc.saveToDb([...])` call proves that.
- **Every `WIKI.configSvc.saveToDb([...])` call site** (`server/setup.js`, `server/core/auth.js`,
  `server/core/letsencrypt.js`, and the GraphQL resolvers `system.js`, `mail.js`, `theming.js`,
  `navigation.js`, `site.js`, `localization.js`, `authentication.js`) — found by `grep -rl
  "saveToDb(\["`, this is the exhaustive, code-verified list of every key ever persisted to the
  `settings` table (`server/core/config.js`'s `saveToDb()` is literally
  `INSERT ... ON CONFLICT (key) ...` per key in its array argument). The union of every array
  argument across all nine call sites is **the complete key list**, 26 keys, tabulated below.

On the 3.0 side: `backend/models/sites.ts:90-192` (the `createSite()` default `config` object) and
`backend/models/settings.ts:39-161` (the `Settings.init()` default rows), both read directly rather
than inferred, plus `backend/db/schema.ts`'s `authentication`/`storage` table definitions and every
`backend/modules/{authentication,storage}/*/definition.yml` for the per-module `config` shape.

[`backend/test/migration-field-mapping-doc.test.ts`](../../backend/test/migration-field-mapping-doc.test.ts)
cross-checks this document's key inventory against the vendored 2.x sources and the live 3.0
model/schema files — it runs as part of `npm run test` from `backend/`; see that file for exactly
what it asserts.

## Part 1 — `settings` table: all 26 2.5.x keys

### Summary: where each key lands, and per-site vs. instance-wide

2.x had exactly one wiki per database, so *every* 2.x setting was trivially "global" — there was
nothing else it could be scoped to. 3.0 introduces real multi-site, so each key below had to be
individually decided: does it become part of `sites.config` (one value **per site**), stay a 3.0
`settings` row (**one value for the whole instance**, same as 2.x), or land nowhere. `mail` is the
clearest instance-wide case — 3.0 keeps exactly one `mail` settings row no matter how many sites
exist, because a wiki has one outbound SMTP relay, not one per hostname — but it is not the only one:
`api`, `auth` (the certs/session-secret one — distinct from `sites.config.auth`, see below),
`flags`, `security`, and `metrics` are instance-wide too, for the same reason (a CSP policy, an
upload size cap, or a signing keypair is a deployment-level fact, not a per-site one).

| 2.x `settings.key` | 3.0 destination                                             | Scope in 3.0                    | Notes                                                          |
| ------------------- | ------------------------------------------------------------ | -------------------------------- | --------------------------------------------------------------- |
| `api`                | `settings` key `api`                                         | **instance-wide** (unchanged)     | `{ isEnabled }` on both sides, verbatim — see [`api`](#api)      |
| `auth`               | split — see [`auth`](#auth)                                  | **split**                        | JWT fields (`audience`/`tokenExpiration`/`tokenRenewal`) → NO DESTINATION; `autoLogin`/`hideLocal` → `sites.config.auth` (per-site); `enforce2FA` → `authentication.config.enforceTfa` on the `local` module row (per-site, per-provider); `loginBgUrl` → the `loginBg` site asset (per-site, not a config field at all) |
| `certs`              | `settings` key `auth`.`certs`                                | **instance-wide**                 | folds into 3.0's differently-shaped `auth` settings key — see [`certs`](#certs-and-sessionsecret) |
| `company`            | `sites.config.company`                                        | **per-site**                     | direct                                                          |
| `contentLicense`     | `sites.config.contentLicense`                                 | **per-site**                     | direct                                                          |
| `editShortcuts`      | **NO DESTINATION**                                            | —                                 | no editor-shortcut-button config anywhere in `sites.ts`          |
| `features`           | `sites.config.features`                                       | **per-site**                     | partial rename — see [`features`](#features)                    |
| `flags`              | `settings` key `flags`                                        | **instance-wide** (unchanged)     | `sqllog`→`sqlLog` rename; `ldapdebug`→NO DESTINATION — see [`flags`](#flags) |
| `footerOverride`     | `sites.config.footerExtra`                                    | **per-site**                     | rename                                                           |
| `graphEndpoint`      | **NO DESTINATION**                                            | —                                 | GraphQL removed entirely (repo `CLAUDE.md`)                      |
| `host`               | `sites.hostname`                                               | **per-site**                     | real column, not `sites.config` — see [`host`](#host)            |
| `lang`               | `sites.config.locales`                                         | **per-site**                     | partial — see [`lang`](#lang)                                    |
| `letsencrypt`        | **NO DESTINATION**                                            | —                                 | see [`letsencrypt`](#letsencrypt)                                 |
| `logo`               | `sites.config.assets.logo`                                     | **per-site**                     | `hasLogo`→boolean flag; `logoIsSquare`→NO DESTINATION — see [`logo`](#logo) |
| `logoUrl`            | the `logo` site asset                                          | **per-site**                     | not a config field at all — same pattern as `loginBgUrl` above; presence is `sites.config.assets.logo` (boolean), the image bytes live in the `siteAssets` table, read via `models/sites.ts`'s `getAsset()` |
| `mail`               | `settings` key `mail`                                          | **instance-wide** (unchanged)     | near-verbatim — see [`mail`](#mail)                               |
| `nav`                | **NO DESTINATION**                                            | —                                 | `{ mode: 'MIXED'\|... }` display toggle has no 3.0 equivalent (not to be confused with the real per-site `navigation` table, which is the `pageTree`/nav-items successor of a *different* 2.x concept) |
| `pageExtensions`     | `sites.config.pageExtensions`                                  | **per-site**                     | direct                                                           |
| `security`           | `settings` key `security`                                      | **instance-wide** (new — see below) | direct-ish renames — see [`security`](#security)                 |
| `seo`                | `sites.config.description` + `sites.config.robots`             | **per-site**                     | partial — see [`seo`](#seo)                                      |
| `server`             | **NO DESTINATION**                                             | —                                 | `sslRedir` — no in-app TLS-redirect toggle in 3.0                 |
| `sessionSecret`      | `settings` key `auth`.`secret`                                 | **instance-wide**                 | folds into the same 3.0 `auth` row as `certs` — see [`certs`](#certs-and-sessionsecret) |
| `telemetry`          | **NO DESTINATION**                                             | —                                 | see [`telemetry`](#telemetry) — not the same thing as 3.0's unrelated `metrics` key |
| `theming`            | `sites.config.theme`                                            | **per-site**                     | partial — see [`theming`](#theming)                               |
| `title`              | `sites.config.title`                                             | **per-site**                     | direct                                                           |
| `uploads`            | `settings` key `security` (moved tables *and* keys)             | **instance-wide** (moved from per-site-shaped in 2.x) | see [`uploads`](#uploads) — the biggest scope surprise in this table |

That is all 26 — every array ever passed to `WIKI.configSvc.saveToDb([...])` across
`server/setup.js`, `server/core/auth.js`, `server/core/letsencrypt.js`,
`server/graph/resolvers/{system,mail,theming,navigation,site,localization,authentication}.js`,
de-duplicated. `search` (`{ maxHits: 100 }`) and `cors` (`{ credentials, maxAge, methods, origin }`)
also appear in `data.yml`'s `defaults.config` block but **never** appear in any `saveToDb` call — they
are `config.yml`-only file defaults in 2.x, never written to the `settings` **table**, so an importer
reading the 2.x `settings` table will never encounter a `search` or `cors` row to map in the first
place. They are noted here only so their absence from the 26 isn't mistaken for an oversight.

### Per-key detail

#### `api`

`{ isEnabled: boolean }` on both sides (`server/graph/resolvers/authentication.js`'s
`updateFlags`/`setApiState`-equivalent → `WIKI.config.api.isEnabled = args.enabled`; 3.0
`settings.ts`'s `key: 'api', value: { isEnabled: false }`). Direct, instance-wide, no transform.

#### `auth`

2.x shape (`data.yml` + `server/setup.js`): `autoLogin`, `enforce2FA`, `hideLocal`, `loginBgUrl`,
`audience`, `tokenExpiration`, `tokenRenewal`. Every field goes somewhere different — this is the
messiest key in the table:

| 2.x `auth.*` field                             | 3.0 destination                                             | Notes                                                                                                     |
| ----------------------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `autoLogin`                                     | `sites.config.auth.autoLogin`                                  | direct rename to per-site (field name unchanged)                                                            |
| `hideLocal`                                     | `sites.config.auth.hideLocal`                                  | direct, per-site                                                                                             |
| `loginBgUrl`                                    | the `loginBg` per-site asset (`siteAssetKinds` in `sites.ts`)  | **not a config field in 3.0 at all** — 2.x stored an external image URL; 3.0 uploads and stores the image itself (`sites.config.assets.loginBg` boolean flag + the actual bytes via `POST /_site/:id/loginBg`). An importer must fetch the URL and upload it as an asset, not copy a string |
| `enforce2FA`                                    | `authentication.config.enforceTfa` on the site's `local` module row | **moves out of `sites.config` entirely** — 3.0's `local` auth module declares `enforceTfa` as one of its own `config` props (`backend/modules/authentication/local/definition.yml`), so this becomes a per-provider, per-site setting rather than a single global boolean |
| `audience`, `tokenExpiration`, `tokenRenewal`   | **NO DESTINATION**                                              | 3.0 has no JWT audience/expiration config anywhere (`backend/base.yml`, `config.sample.yml` confirmed clean of `jwt`/`audience`/`tokenExpiration`) — session auth in 3.0 is `@fastify/session` cookie-based (see `certs`/`sessionSecret` below), and JWTs are not part of that model the way 2.x's passport-jwt strategy required |

#### `certs` and `sessionSecret`

Two separate 2.x settings keys fold into **one** 3.0 `settings` row, `key: 'auth'` (not to be
confused with `sites.config.auth` above — 3.0 reuses the string `'auth'` for a completely different,
instance-wide settings row):

| 2.x key(s)                  | 3.0 `settings.auth.*` field | Notes                                                                                                     |
| ---------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `certs` (`{ jwk, public, private }`) | `certs`                        | direct — both are the RSA keypair generated at install, still present in 3.0 (`generateSigningCertificates()` in `backend/models/apiKeys.ts`), just repurposed to sign API keys instead of JWTs |
| `sessionSecret`              | `secret`                       | rename; both are a random 32-byte hex string, but 2.x used it to sign JWTs/passport sessions and 3.0 uses it to sign `@fastify/session` cookies exclusively (per the doc-comment in `backend/models/settings.ts`) |
| (none)                       | `rootAdminGroupId`, `rootAdminUserId`, `guestUserId` | **new in 3.0, no 2.x source** — these are the seeded `SystemIds` UUIDs, always freshly generated per install |

#### `features`

| 2.x `features.*`      | 3.0 `sites.config.features.*` | Notes                                                                                   |
| ----------------------- | -------------------------------- | ------------------------------------------------------------------------------------------ |
| `featurePageRatings`    | `ratings`                        | rename; 3.0 additionally splits out `ratingsMode` (`'off'` by default) with no 2.x source |
| `featurePageComments`   | `comments`                       | rename                                                                                     |
| `featurePersonalWikis`  | **NO DESTINATION**                | no personal-wiki-per-user concept anywhere in 3.0's `sites.ts`                             |
| (none)                  | `browse`, `collaborativeEditing`, `profile`, `reasonForChange`, `search` | **new in 3.0, no 2.x source** |

#### `flags`

2.x `{ ldapdebug, sqllog }` → 3.0 `settings.flags = { experimental, authDebug, sqlLog }`. `sqllog` →
`sqlLog` is a direct rename (both instance-wide, both a DB query-logging toggle). `ldapdebug` is
**NO DESTINATION** — there is no `ldap` directory under `backend/modules/authentication/` (see
[Part 2](#part-2--authentication-table) below), so a flag that only ever gated LDAP debug logging has
nothing left to gate. `experimental` and `authDebug` are new in 3.0 with no 2.x source.

#### `host`

Lands on `sites.hostname`, a real `varchar` **column** on the `sites` table
(`backend/db/schema.ts:624`), not a `sites.config` JSON path — the one 2.x settings key in this table
that becomes a first-class column rather than a config value. Per-site, obviously (`hostname` is
`unique()` per row). The trailing-slash trim 2.x's `site.js` resolver applies (`siteHost.endsWith('/')
→ slice(0, -1)`) is a formatting detail an importer should replicate, not a mapping concern.

#### `lang`

2.x `{ code, autoUpdate, namespaces, namespacing, rtl }` → 3.0 `sites.config.locales = { primary,
active, forcePrefix, showMenu }`.

| 2.x `lang.*`  | 3.0 destination                    | Notes                                                                                                   |
| -------------- | ------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| `code`         | `sites.config.locales.primary`       | rename                                                                                                       |
| `autoUpdate`   | **NO DESTINATION**                    | 2.x auto-downloaded locale string updates from Requarks' translation service — dead along with `graphEndpoint`/GraphQL (same removal as the `graphEndpoint` key above; both were part of the same phone-home sync feature) |
| `namespaces`   | **NO DESTINATION**                    | no i18n namespace concept found in `sites.ts`/`backend/locales/`; 3.0's locale strings are a flat `en.json` per the repo's own layout docs |
| `namespacing`  | **NO DESTINATION**                    | same as `namespaces`                                                                                          |
| `rtl`          | **NO DESTINATION**                    | no right-to-left flag on `sites.config` or on the (out-of-scope) locale metadata — worth a follow-up spot-check against `backend/locales/metadata.js`, not assumed gone without checking further |
| (none)         | `active`, `forcePrefix`, `showMenu`  | **new in 3.0, no 2.x source** — `active` is meaningful only once multi-locale sites exist, which 2.x never had |

#### `letsencrypt`

**NO DESTINATION**, whole key. `server/core/letsencrypt.js` is the entire 2.x ACME/Let's Encrypt
integration — automatic certificate issuance and renewal, config persisted under this key. 3.0 has no
equivalent anywhere: `config.sample.yml`'s `ssl:` block is a plain enable/cert-path/key-path trio (no
ACME), and no `letsencrypt`/`acme`/`certbot` string appears anywhere under `backend/`. TLS termination
in 3.0 is assumed to be handled outside the app (reverse proxy), consistent with `server`/`sslRedir`
below also having no destination.

#### `logo`

`{ hasLogo: boolean, logoIsSquare: boolean }`, set once in `server/setup.js` at install and never
touched again anywhere else in the 2.x codebase (confirmed: `grep -rn "hasLogo\|logoIsSquare"
server/` in the vendored 2.x tree matches only `setup.js`) — logo upload in 2.x is actually driven
through a separate file-write path keyed off `WIKI.config.logoUrl`/an uploaded file, not this settings
key, so `hasLogo`/`logoIsSquare` are effectively dead weight that only ever held their install-time
default. `hasLogo` maps loosely to 3.0's `sites.config.assets.logo` boolean (both answer "is a logo
image present"), but there is no real behavioral continuity to preserve — an importer can treat this
as derived (does a 2.x logo file/URL actually exist?) rather than copied. `logoIsSquare` is
**NO DESTINATION** — no aspect-ratio hint exists anywhere in `sites.ts`.

#### `mail`

Near-verbatim, instance-wide on both sides — the clearest globally-scoped case in the whole table,
per the task description. Every 2.x field name (`senderName`, `senderEmail`, `host`, `port`, `name`,
`secure`, `verifySSL`, `user`, `pass`, `useDKIM`, `dkimDomainName`, `dkimKeySelector`,
`dkimPrivateKey`) is present verbatim in 3.0's `settings.ts` `mail` row. The one addition,
`defaultBaseURL` (`'https://wiki.example.com'`), is **new in 3.0 with no 2.x source** — and its
existence is itself evidence for *why* `mail` had to stay instance-wide rather than move to
`sites.config`: 2.x's mail templates linked back to the single wiki using the single global `host`
setting, but 3.0 has one `mail` row shared across every site (each with its own `hostname`), so it
needs its own fallback base URL rather than inferring one from "the" site.

Every field is a straight copy; `pass` is the one field 2.x's own `MailQuery.config` resolver already
masks in transit (`'********'` placeholder) — an importer reading the raw DB value bypasses that UI
masking and gets the real value, which is correct for a migration (not a display path).

#### `security`

2.x's `security` key was global by necessity (2.x had no multi-site to scope it to); 3.0 keeps it
global by choice — a CSP policy, HSTS duration, or trust-proxy flag is a deployment/network-topology
fact, not something that differs page-to-page on the same running server, so it stayed instance-wide
rather than moving into `sites.config` the way `company`/`title`/`theme` did.

| 2.x `security.*`             | 3.0 `settings.security.*`         | Notes                                                                                     |
| ------------------------------ | ------------------------------------ | ---------------------------------------------------------------------------------------------- |
| `securityOpenRedirect`         | `disallowOpenRedirect`               | **inverted polarity, not a plain rename**: 2.x `true` = allow, 3.0 field is a `disallow*` flag — a 2.x `true` must be written as 3.0 `false` and vice versa |
| `securityIframe`               | `disallowIframe`                     | same inversion as above                                                                        |
| `securityReferrerPolicy`       | `enforceSameOriginReferrerPolicy`    | rename, same polarity (both `true` = policy is enforced)                                       |
| `securityTrustProxy`           | `trustProxy`                         | direct rename, same polarity                                                                    |
| `securitySRI`                  | **NO DESTINATION**                    | no Subresource-Integrity toggle anywhere in `settings.ts`                                       |
| `securityHSTS`                 | `enforceHsts`                        | rename, same polarity                                                                           |
| `securityHSTSDuration`         | `hstsDuration`                       | rename                                                                                           |
| `securityCSP`                  | `enforceCsp`                         | rename, same polarity                                                                           |
| `securityCSPDirectives`        | `cspDirectives`                      | rename                                                                                           |
| (none)                         | `corsConfig`, `corsMode`             | **new in 3.0, no 2.x source** — 2.x's CORS behavior was framework-default, never configurable    |
| (none, see `uploads` below)    | `forceAssetDownload`, `uploadMaxFileSize`, `uploadScanSVG` | **moved from the 2.x `uploads` key** — see [`uploads`](#uploads) |

#### `seo`

2.x `{ description, robots: ['index','follow'], analyticsService, analyticsId }`, set at
`server/setup.js` install time and updated wholesale by `server/graph/resolvers/site.js`'s
`updateConfig`.

| 2.x `seo.*`         | 3.0 destination                          | Notes                                                                                                  |
| --------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `description`         | `sites.config.description`                  | direct, per-site                                                                                             |
| `robots`               | `sites.config.robots`                        | **structural transform**: 2.x is a string array that may or may not contain `'index'`/`'follow'`; 3.0 is a fixed `{ index: boolean, follow: boolean }` object — presence-in-array becomes a boolean field |
| `analyticsService`     | **NO DESTINATION**                           | no analytics-provider config anywhere in `sites.ts`                                                          |
| `analyticsId`          | **NO DESTINATION**                           | same as `analyticsService`                                                                                    |
| (none)                 | `sitemap`, `discoverable`                    | **new in 3.0, no 2.x source** — 2.x's closest equivalent was the presence of `'index'` in the `robots` array, which is not the same thing as a dedicated sitemap toggle |

#### `server`

2.x `{ sslRedir: boolean }` (HTTP→HTTPS redirect toggle, `server/graph/resolvers/system.js`'s
`setHTTPSRedirection`). **NO DESTINATION** — no equivalent flag anywhere in 3.0's `settings.ts` or
`sites.ts`; consistent with `letsencrypt` above, in-app TLS handling appears to have been dropped in
favor of assuming a reverse proxy in front of 3.0.

#### `telemetry`

2.x `{ isEnabled: boolean, clientId: string }` — a phone-home anonymous-usage-stats toggle with a
per-install random id (`server/graph/resolvers/system.js`'s `setTelemetry`/
`resetTelemetryClientId`). **NO DESTINATION**: no `telemetry` key exists in `backend/models/
settings.ts`. This is *not* the same thing as 3.0's `metrics` settings key (`{ isEnabled }`) — that
one gates a Prometheus scrape endpoint (confirmed: `backend/api/system/settings.ts`'s own schema description
reads "Whether the Prometheus metrics endpoint is turned on", and `backend/locales/en.json`'s
`admin.metrics.subtitle` says "Manage the Prometheus metrics endpoint") — an unrelated 3.0-only
feature that happens to share the word "metrics", not a rename of `telemetry`. Worth flagging for a
human, not an importer: `backend/locales/en.json` still carries unused
`admin.utilities.telemetryTitle`/`telemetrySubtitle` strings with nothing behind them in
`frontend/src/pages/AdminUtilities.vue` (no `telemetry` reference there at all) — this reads as an
unported GraphQL-era admin panel (per the repo's own "GraphQL was removed" note in `CLAUDE.md`)
rather than a
deliberate product decision to drop telemetry, so a future feature reviving it would likely reuse
those exact locale keys.

#### `theming`

2.x `{ theme, iconset, darkMode, tocPosition, injectCSS, injectHead, injectBody }` → 3.0
`sites.config.theme` (a much larger object, per-site).

| 2.x `theming.*` | 3.0 `sites.config.theme.*` | Notes                                                                                                        |
| ----------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `darkMode`         | `dark`                         | rename                                                                                                         |
| `tocPosition`       | `tocPosition`                  | direct                                                                                                         |
| `injectCSS`         | `injectCSS`                    | direct (2.x minifies it server-side via `CleanCSS` before storing; 3.0's schema doesn't say either way — worth a spot-check, not assumed) |
| `injectHead`        | `injectHead`                   | direct                                                                                                         |
| `injectBody`        | `injectBody`                   | direct                                                                                                         |
| `theme`             | **NO DESTINATION**              | 2.x selected one of a small set of named prebuilt themes (`'default'`, …) by key; 3.0 has no theme-name selector at all — it exposes discrete color tokens instead (`colorPrimary`/`colorSecondary`/`colorAccent`/`colorHeader`/`colorSidebar`), so a 2.x theme name has nothing to copy into and would need a lookup table of "what did the `default` 2.x theme's colors actually resolve to" to approximate, which this doc does not attempt |
| `iconset`           | **NO DESTINATION**              | 2.x picked one global icon font (`mdi`, `fa`, …); 3.0's icon system is Iconify-based with per-set enable/disable, not a single active iconset (see the repo's own `CLAUDE.md` Icons section) — no single field to land in |
| (none)              | `codeBlocksTheme`, `colorPrimary`, `colorSecondary`, `colorAccent`, `colorHeader`, `colorSidebar`, `contentWidth`, `sidebarPosition`, `showPrintBtn`, `baseFont`, `contentFont` | **new in 3.0, no 2.x source** — all default to `sites.ts`'s hardcoded values on import |

#### `uploads`

**The biggest scope surprise in this table.** 2.x `{ maxFileSize, maxFiles, scanSVG, forceDownload }`
does **not** land in 3.0's per-site `sites.config.uploads` — that 3.0 object exists but only holds
one unrelated new field, `conflictBehavior` (`sites.ts:189-191`). Instead, every 2.x `uploads.*`
field except `maxFiles` reappears **renamed, under the instance-wide `security` settings key**;
`maxFiles` has no 3.0 destination — 3.0 dropped the never-enforced `security.uploadMaxFiles` setting
it would have mapped to (WP 2174), since every upload route takes exactly one file per request and
there is no batch to cap:

| 2.x `uploads.*` | 3.0 `settings.security.*` | Notes                                            |
| ------------------ | ----------------------------- | --------------------------------------------------- |
| `maxFileSize`       | `uploadMaxFileSize`            | rename, moved out of `uploads` entirely into `security` |
| `maxFiles`          | **NO DESTINATION**             | `security.uploadMaxFiles` was removed as a dead key nothing ever enforced (single-file-per-request uploads have no batch to cap) — OpenProject #1360/#2152/#2174, 2026-08-24 security audit |
| `scanSVG`           | `uploadScanSVG`                | same move — now enforced: an uploaded `.svg` is sanitized when this is on (OpenProject #2170), alongside the unconditional per-response Content-Security-Policy on every SVG/HTML-typed asset reply (`helpers/security.ts#SVG_CSP`) |
| `forceDownload`     | `forceAssetDownload`           | rename + same move                                   |

In other words: the 2.x key named `uploads` maps to 3.0's `security` settings key, not to 3.0's
identically-named `uploads` object — matching names across versions is not a safe signal here. This
also means upload limits go from (trivially) global in 2.x to **deliberately instance-wide** in 3.0,
not per-site — a large-file cap is treated as a server-resource concern shared by every site, the
same reasoning as the rest of `security`.

## Part 2 — `authentication` table

Column-level mapping already exists in `2.5x-to-3.0-mapping.md`'s `## authentication` section and is
not repeated in full here — this section only adds what that doc's own scope note leaves open: the
provider-by-provider (`key`/`module`) inventory.

### Confirmed no-destination 2.x auth providers

3.0 ships sixteen authentication modules as of this writing (`ls backend/modules/authentication/`):
`auth0`, `cas`, `discord`, `github`, `gitlab`, `google`, `keycloak`, `ldap`, `local`, `microsoft`,
`oauth2`, `oidc`, `okta`, `saml`, `slack`, `twitch`. This list has grown since this doc was first
authored — `ldap`, `saml`, `cas`, `keycloak`, `discord`, `slack`, `auth0`, `gitlab`, `microsoft`,
`okta`, `oauth2`, and `twitch` all gained a `modules/authentication/<key>/` directory after the
"four originally-surviving modules" spot-check below was written, and have not yet had the same
`config` prop-name check applied to them — that is real follow-up scope, not something to fabricate
here.

2.x ships twenty-one providers (`ls server/modules/authentication/` in the vendored 2.x tree —
fetched 2026-08-17): `auth0`, `azure`, `cas`, `discord`, `dropbox`, `facebook`, `firebase`, `github`,
`gitlab`, `google`, `keycloak`, `ldap`, `local`, `microsoft`, `oauth2`, `oidc`, `okta`, `rocketchat`,
`saml`, `slack`, `twitch`. Sixteen keys match by directory name; the other **five have no
`modules/authentication/<key>/` directory in this repo and are confirmed NO DESTINATION**:

`azure`, `dropbox`, `facebook`, `firebase`, `rocketchat`

A 2.x `authentication` row whose `strategyKey` is one of these five has nowhere to land: not
just its `config` blob (the "key-by-key remap" caveat `2.5x-to-3.0-mapping.md` already documents for
*existing* modules) but the row itself, and therefore every `users.auth[authModuleId]` entry that
depended on it. An importer must treat this as a hard skip-or-flag case, not a config-remap case —
there is no module for the remap to target. (`ldap` now existing means the `flags.ldapdebug` NO
DESTINATION finding above is about the debug-logging config prop specifically, not about the module
being absent — 3.0's `ldap` module has no equivalent debug flag.)

### The four originally-surviving modules' `config` prop-name check

`2.5x-to-3.0-mapping.md` already spot-checks `local` in full. A light pass on the other three
(matching that doc's [Module config remapping](2.5x-to-3.0-mapping.md#module-config-remapping)
methodology, not repeating its depth):

- **`google`**: `clientId`, `clientSecret`, `hostedDomain` keep identical names on both sides. 3.0
  adds `allowUnverifiedEmail` (new, no 2.x source).
- **`github`**: `clientId`, `clientSecret` keep identical names. 2.x's `useEnterprise` (boolean) +
  `enterpriseDomain` (string) pair becomes one 3.0 field, `enterpriseHost` — **not a rename**, a
  structural collapse: presence of a non-empty `enterpriseHost` string implies what the 2.x boolean
  used to gate explicitly. 3.0 adds `allowedOrganization` (new, no 2.x source).
- **`oidc`**: `clientId`, `clientSecret`, `authorizationURL`, `tokenURL`, `userInfoURL` keep
  identical names. 3.0 adds `issuer`, `useDiscovery`, `jwksURL`, `scopes`, `emailClaim`,
  `displayNameClaim`, `logoutURL` (all new, no 2.x source — largely because 3.0 added OIDC discovery
  document support that 2.x's OIDC module never had). 2.x's `skipUserProfile` prop was not
  cross-checked against 3.0's list here and should be spot-checked before an importer trusts a
  straight copy of every `oidc` config key.

A full per-prop reconciliation of these three (mirroring `git`/`s3`'s depth in the column-level doc)
is left as follow-up scope, same as that doc already does for the storage modules it didn't
spot-check.

## Part 3 — `storage` table

Column-level mapping already exists in `2.5x-to-3.0-mapping.md`'s `## storage` section, including the
two confirmed no-destination **columns** the task description asks to be marked explicitly:

- **`mode`** (`'sync'`/`'push'`/`'pull'`) — no `mode` column on 3.0's `storage` table at all.
- **`syncInterval`** — no dedicated column either; sync scheduling is "not modelled yet" per the
  `git` module's own `definition.yml` comment.

Both are re-confirmed here directly against `backend/db/schema.ts:648-672`: the six 3.0 `storage`
columns are `id`, `module`, `isEnabled`, `contentTypes`, `assetDelivery`, `versioning`, `config`,
`state`, `siteId` — no `mode`, no `syncInterval` among them.

### Confirmed no-destination 2.x storage modules

3.0 ships seven storage modules (`ls backend/modules/storage/`): `azure`, `db`, `disk`, `gcs`, `git`,
`s3`, `sftp`. 2.x ships eleven (`ls server/modules/storage/` in the vendored 2.x tree): `azure`,
`box`, `digitalocean`, `disk`, `dropbox`, `gdrive`, `git`, `onedrive`, `s3`, `s3generic`, `sftp`. Five
keys match by directory name (`azure`, `disk`, `git`, `s3`, `sftp`); the other **six have no
`modules/storage/<key>/` directory in this repo and are confirmed NO DESTINATION**:

`box`, `digitalocean`, `dropbox`, `gdrive`, `onedrive`, `s3generic`

Note `digitalocean` and `s3generic` in particular: both are S3-*compatible* targets that a naive
reading might assume fold into 3.0's `s3` module (which does add a `mode: 'do'|'custom'` selector
precisely for DigitalOcean Spaces and custom S3-compatible endpoints — see
`2.5x-to-3.0-mapping.md`'s `s3` module remapping). They do not: 2.x stored these as **entirely
separate module `key`s** with their own `storage` table rows, `isEnabled` flags, and `config` blobs,
independent of the `s3` row. An importer would need to actively fold a 2.x `digitalocean`/`s3generic`
row's config into the *same site's* `s3` row (setting `mode: 'do'`/`'custom'` and copying the
matching fields) — a genuine cross-row merge, not a per-row rename, and only possible if the site
doesn't already have its own separate `s3` row that would conflict.

3.0's `db` module (storing content directly in Postgres) has **no 2.x counterpart at all** — new
capability, no source data to migrate into it, not a mapping gap. Same for `gcs` (Google Cloud
Storage) — 2.x's storage modules never covered it.
