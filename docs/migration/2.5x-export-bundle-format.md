# 2.5.x Export-to-Disk bundle format reference

Precise reference for the bundle a 2.5.x MySQL/MariaDB/MSSQL/SQLite install produces via
**Admin Area → Utilities → Export**, produced for the source-connector / schema-mapping spike
(Feature 412). This is what a bundle-import path — as opposed to a live-Postgres source connection —
actually has to unpack, alongside [`2.5x-source-schema.md`](2.5x-source-schema.md), which this doc
assumes as background for column-level detail on the tables named below.

## Sources

- [`server/graph/resolvers/system.js`](https://github.com/requarks/wiki/blob/main/server/graph/resolvers/system.js)
  — the `export` mutation and `exportStatus` query resolvers (the GraphQL surface the admin UI
  calls).
- [`server/core/system.js`](https://github.com/requarks/wiki/blob/main/server/core/system.js) — the
  `WIKI.system.export()` implementation the resolver kicks off (fire-and-forget, not awaited by the
  mutation).
- [`server/models/authentication.js`](https://github.com/requarks/wiki/blob/main/server/models/authentication.js)
  — consulted to confirm `authentication.strategyKey` / `.displayName` (selected by the `settings`
  export case) are real, if late-added, columns; see the erratum in `2.5x-source-schema.md`.
- Unmodified copies of all three are vendored in [`vendor/export-bundle/`](vendor/export-bundle/) for
  provenance, and are cross-checked against this doc by
  [`verify-export-bundle-doc.test.mjs`](verify-export-bundle-doc.test.mjs) — run
  `node --test docs/migration/verify-export-bundle-doc.test.mjs` from the repo root.

## The shape of a launch

`export` is a GraphQL **mutation** (`SystemMutation.export`), not a query: it validates inputs, then
calls `WIKI.system.export({ entities, path })` **without awaiting it** and returns
`"Export started successfully."` immediately. The actual work happens in the background; the admin UI
is expected to poll `SystemQuery.exportStatus` separately. Before starting, the resolver:

- Resolves `args.path` against `WIKI.ROOTPATH` (so a relative path is server-root-relative, not
  cwd-relative).
- Refuses to start if another export is already `running` (`WIKI.system.exportStatus.status`) — the
  whole feature is single-run, there is no concurrent-export support.
- Requires `args.entities.length >= 1` — you cannot export "nothing".
- Calls `fs.ensureDir(desiredPath)` then **requires the target directory to be empty**
  (`fs.readdir(desiredPath).length` must be `0`), throwing `'Target directory must be empty!'`
  otherwise. Every real bundle therefore starts life as an empty directory — an importer never has to
  worry about stray pre-existing files mixed into a genuine bundle.

`args.entities` is a checklist the admin UI presents as independent checkboxes; **any subset is
valid and normal**. A bundle produced with only `pages` selected is a complete, correct bundle for
that selection — an importer must not assume all seven/eight files listed below are present, and
must treat each one as independently optional.

## No archive wrapper — it is a plain directory tree

There is no tar/zip/archive step anywhere in either file — every write goes straight to
`opts.path` (the directory the admin chose) via `fs.outputFile`, `fs.outputJSON`, or
`fs.createWriteStream`, and neither vendored file `require()`s `tar`, `archiver`, `adm-zip`, or any
other archive library. **The "export" is nothing more than a directory the server populated
in-place** — an importer reads it as a plain filesystem tree, not by unpacking anything.

## The eight export entities and their files

`args.entities` selects among **eight** `switch`-case keys in `WIKI.system.export()`; seven produce a
single named file directly under the export root, one (`assets`) produces a raw-file directory tree.
Progress is split **evenly across however many entities were selected** —
`progressMultiplier = 1 / opts.entities.length` — regardless of each entity's actual data volume, so
picking `assets` (potentially gigabytes) alongside `navigation` (a few KB) reports each as an equal
50% share of the run; see [Progress reporting](#progress-reporting-and-its-quirks) below.

| Entity       | Output                                                 | Compressed? | Streamed in batches?                   |
| ------------ | ------------------------------------------------------ | ----------- | -------------------------------------- |
| `users`      | `users.json.gz`                                        | gzip        | yes, 50/batch                          |
| `groups`     | `groups.json`                                          | plain       | no — one query                         |
| `pages`      | `pages.json.gz`                                        | gzip        | yes, 10/batch                          |
| `history`    | `pages-history.json.gz`                                | gzip        | yes, 10/batch                          |
| `comments`   | `comments.json.gz`                                     | gzip        | yes, 50/batch                          |
| `navigation` | `navigation.json`                                      | plain       | no — one query                         |
| `settings`   | `settings.json`                                        | plain       | no — several queries                   |
| `assets`     | `assets/{folderPath}/{filename}` (raw files, not JSON) | none        | streamed, unbatched (single DB cursor) |

Every gzip'd file is written by the exact same three-stage pipeline: a hand-built Transform that
wraps a stream of JS objects into pretty-printed JSON-array text (`JSON.stringify(chunk, null, 2)`,
2-space indent, matching `fs.outputJSON`'s own `{ spaces: 2 }` used by the plain files) →
`zlib.createGzip()` → `fs.createWriteStream(outputPath)`. Every plain (non-`.gz`) file is written in
one shot via `fs.outputJSON(outputPath, data, { spaces: 2 })` — no pretty-printing difference between
the two; gzip is purely a compression choice, the JSON _content_ is formatted identically either way.
An entity whose count is `0` is **skipped entirely** — `users`/`pages`/`history`/`comments` each
`COUNT(*)` first and, if zero, log a warning and produce **no file at all** (not an empty
`[]`/`[].gz`). Same for `assets`: zero rows means no `assets/` directory is created.

### `users.json.gz`

Batches of 50, via `WIKI.models.users.query().offset(offset).limit(50)`. Each element is a full
`users` row (every column from `2.5x-source-schema.md`'s `users` table — **including `password`
(the bcrypt hash) and `tfaSecret` in the clear**; a bundle is credential-bearing, not just
content-bearing) plus two denormalized relations added via `withGraphJoined`:

- **`groups`**: array of `{ id, name }` — _not_ the full group row, just enough to resolve group
  membership by name/id.
- **`provider`**: single object `{ key, strategyKey, displayName }` from the `authentication` table
  (see the erratum in `2.5x-source-schema.md` — `strategyKey`/`displayName` only exist from
  `2.5.1.js` onward, so a bundle from an install that somehow skipped that migration would have these
  as `''`, not absent).

### `groups.json`

**Not batched at all** — a single `WIKI.models.groups.query()` with no relation joins, output
verbatim as a plain (uncompressed) JSON array of full `groups` rows (`id`, `name`, `permissions`,
`pageRules`, `isSystem`, `createdAt`, `updatedAt`, `redirectOnLogin`). No membership list is embedded
here — group membership only appears from the `users` side (`users[].groups`), so reconstructing a
group's member list from the bundle alone requires scanning all of `users.json.gz`, not reading
`groups.json`.

### `pages.json.gz`

Batches of 10, via `WIKI.models.pages.query().offset(offset).limit(10)`. Each element is a full
`pages` row plus:

- **`author`** and **`creator`**: each `{ id, name, email, providerKey }` — two separately-joined
  copies of the same shape (Wiki.js pages track "who wrote the current content" separately from "who
  originally created the page"). `authorId`/`creatorId` integer columns are **also still present** on
  the row alongside these nested objects — the export is redundant here, not a replacement of the FK
  column with the joined object.
- **`tags`**: array of `{ tag, title }` — just the tag string and its display title, not the full
  `tags` row (no `id`, no `createdAt`).

### `pages-history.json.gz`

Batches of 10, via `WIKI.models.pageHistory.query().offset(offset).limit(10)`. Each element is a full
`pageHistory` row plus:

- **`author`**: `{ id, name, email, providerKey }` (same shape as `pages.author` above).
- **`page`**: `{ id, title, path, localeCode }` — the **parent page** is denormalized inline here too,
  not just left as the row's existing `pageId` integer column (which also remains present, unenforced
  FK as documented in `2.5x-source-schema.md`).
- **`tags`**: array of `{ tag, title }`, same shape as `pages.tags`.

### `comments.json.gz`

Batches of 50, via `WIKI.models.comments.query().offset(offset).limit(50)`. Each element is a full
`comments` row plus:

- **`author`**: `{ id, name, email, providerKey }`. For a guest comment (no registered `authorId`),
  the row's own `name`/`email` columns — added in `2.4.36.js` specifically for guest comments — are
  what actually carries the identity; `author` would be `null`/absent in that case since the join has
  nothing to match.
- **`page`**: `{ id, path, localeCode, title }` — note the field **order** differs from
  `pages-history.json.gz`'s `page` object (`id, path, localeCode, title` here vs.
  `id, title, path, localeCode` there); same four fields, different `.select()` call, cosmetic but
  worth knowing if a consumer diffs raw JSON text rather than parsing it.

### `navigation.json`

**Not** a row-array dump of the `navigation` table. The resolver reduces the table's `(key, config)`
rows into a single **keyed object**: `{ [row.key]: row.config, ... }`. An importer reading this file
gets one JSON object whose top-level keys _are_ the navigation config keys (per-site nav trees etc.),
not an array it can iterate with a `.map()` expecting `{key, config}` shape.

### `settings.json`

**The most surprising file in the bundle: despite the name, this is not a dump of the `settings`
table.** It is the live, already-merged `WIKI.config` object (`config.yml` + `base.yml` defaults +
the db `settings` table, exactly as the running server sees it — i.e. it already reflects whatever
`WIKI.configSvc` folded together at boot, not a table an importer can read column-by-column) spread
into an object, plus a `modules` sub-object added on top:

```
{
  ...WIKI.config,                          // the entire live merged config, not the settings table
  modules: {
    analytics: [...],                      // full analytics table dump
    authentication: [...],                 // full authentication table dump, with two fields unwrapped:
                                            //   domainWhitelist: row.domainWhitelist.v ?? []
                                            //   autoEnrollGroups: row.autoEnrollGroups.v ?? []
    commentProviders: [...],               // full commentProviders table dump
    renderers: [...],                      // full renderers table dump
    searchEngines: [...],                  // full searchEngines table dump
    storage: [...]                         // full storage table dump
  },
  apiKeys: [...]                           // apiKeys table, filtered to isRevoked = false only
}
```

The `domainWhitelist`/`autoEnrollGroups` unwrap matters for a bundle reader: the live `authentication`
row stores those two columns as `{ v: [...] }` (an Objection/knex JSON-wrapper convention seen
elsewhere in this codebase), and the export flattens that away — so `settings.json`'s
`modules.authentication[].domainWhitelist` is a bare array, while the same column read straight out of
a raw `authentication` table row (e.g. by a live-DB source connector, not the bundle path) is not.
`apiKeys` is filtered server-side (`isRevoked = false`) — revoked keys are never in the bundle at all,
by design, not merely redacted.

### `assets` — raw file layout, no JSON

The one entity that isn't a JSON file. Source query:

```
knex.select('filename', 'folderId', 'data').from('assets')
  .join('assetData', 'assets.id', '=', 'assetData.id')
  .stream()
```

For each row, the target path is computed as:

```
filename = (asset.folderId && asset.folderId > 0)
  ? `${assetFolders[asset.folderId]}/${asset.filename}`
  : asset.filename
```

(`assetFolders` = `WIKI.models.assetFolders.getAllPaths()`, a folderId → full nested folder-path
map), then written raw with `fs.outputFile(path.join(opts.path, 'assets', filename), asset.data)` —
i.e. the on-disk layout is exactly **`assets/{folderPath}/{filename}`** under the export root,
`fs.outputFile` creating whatever intermediate directories `folderPath` needs. The bytes written are
the raw `assetData.data` blob, unmodified and uncompressed — no JSON envelope, no sidecar metadata
file per asset.

**This means asset metadata is lost from the bundle** — `id`, `hash`, `mime`, `fileSize`, `kind`,
`authorId`, `createdAt`/`updatedAt` (see `assets` in `2.5x-source-schema.md`) are **not** written
anywhere when only `assets` is selected. An importer reconstructing assets from a bundle has only the
folder path, the filename (including its extension, from which `mime`/`ext` can be _guessed_ but not
recovered exactly — the original `assets.mime` value is never re-derivable with certainty), and the
raw bytes. If asset _metadata_ is also needed, the admin running the export would separately need the
live database (or a Postgres-direct connector), since the export-bundle path structurally cannot
supply it.

## Progress reporting and its quirks

`WIKI.system.exportStatus` (in `server/core/system.js`) is a shared, single in-process object with
fields `status` (`'notrunning' | 'running' | 'success' | 'error'`), `progress` (0–100), `message`,
`startedAt`, and `updatedAt`. The `SystemQuery.exportStatus` resolver returns `status`,
`Math.ceil(progress)`, `message`, `startedAt` — **`updatedAt` is declared on the object but never
assigned anywhere in `export()`**, so it stays `null` for the life of the process; it is not exposed
by the resolver either, so this is a dead field on both sides, not something a polling client can
rely on to detect a stalled export.

Two behaviors worth knowing precisely, since together they are the strongest signal for why an
importer reading a bundle back in should stream rather than load wholesale:

- **Batch size is 10 for `pages`/`history`, 50 for `users`/`comments`** (`assets` uses a single
  unbatched streaming DB cursor, no `.limit()` at all — it never buffers a whole batch of rows, only
  whatever Node's stream internals hold at once). These numbers were chosen by upstream as workable
  units for a page of rows to hold in memory before flushing to the gzip pipeline; an importer
  reversing the process (reading the bundle back into a target DB) should treat similarly-sized
  chunks — not the whole array — as its natural unit of work, both to bound memory and to mirror the
  shape the exporter itself already committed to as safe.
- **The batch-fetch loop has no real backpressure.** `fetchXBatch(offset)` is an `async` function that
  `await`s its own query, pushes rows onto a Readable, then calls `fetchXBatch(offset + N)` again
  **without awaiting it** before returning. Node's `Readable.push()` return value (`false` when the
  internal buffer is full) is never checked, so a fast DB paired with a slow disk/gzip stage can queue
  many batches' worth of rows in memory before the write side catches up — the `.limit(10)`/`.limit(50)`
  choice bounds _one_ batch, not the total in-flight buffer. A source-connector importer built to
  stream should honor backpressure properly (respect `write()`'s return value / use `pipeline()`
  throughout, as the export code does for the _output_ half of its own pipeline) rather than copying
  this specific input-side pattern.

Per-batch progress accounting has its own minor quirk: the increment
(`progressMultiplier / Math.ceil(count / batchSize) * 100`) is added once per `fetchXBatch` call
**including the final, empty, "no more rows" call** that terminates the stream — so the loop fires
`Math.ceil(count / batchSize) + 1` times but was budgeted for exactly `Math.ceil(count / batchSize)`,
meaning an entity's reported progress share slightly overshoots its fair `progressMultiplier * 100`
before the next entity starts. Invisible in practice because `export()` forces `progress = 100` and
`status = 'success'` unconditionally once the entire `entities` loop finishes — but it means
mid-export `progress` values from `exportStatus` are an approximation, not an exact fraction, and
should be treated as a rough indicator by any UI/importer polling it, not a precise byte/row count.

## Implications for the spike's bundle-import path

- Read the target directory as a plain tree — no unpacking step is ever needed or possible.
- Treat every one of the eight files/subtrees as independently optional; check existence before
  reading, never assume a complete set.
- `settings.json` is not the `settings` table — do not attempt to write its top level back into a
  `settings` key/value table; only `modules.*` and `apiKeys` map onto real tables.
- `navigation.json` needs re-expansion from `{key: config}` back into `(key, config)` rows before it
  can be written into a target `navigation` table.
- Denormalized `author`/`creator`/`page`/`tags`/`groups`/`provider` objects are convenience-only;
  the authoritative link is still the row's own FK-shaped id column (`authorId`, `creatorId`,
  `pageId`, `folderId`, etc., all still present alongside the nested object) documented in
  `2.5x-source-schema.md` — resolve identity through the old-id → new-UUID lookup table that doc
  already calls for, not by re-deriving ids from the denormalized copies (which, for `tags`, don't
  even carry an id at all — only `tag`/`title`).
- `assets` gives files + a folder path, nothing else; any importer wanting asset metadata parity needs
  a second source (live DB / Postgres-direct connector) in addition to the bundle.
- Mirror the exporter's own batch sizes (10 or 50 rows) when writing an importer, and use real
  backpressure-respecting streams on both the read and write side — unlike the exporter's own
  fetch-batch loop, which does not.
