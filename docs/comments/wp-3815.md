# WP 3815 comment recommendations

## backend/types/fastify.d.ts, `Session.authFlow`

**Change** (JSDoc above the field):

Current:

```
/**
 * The redirect login in progress: an answer whose `state` is not the one this session sent is
 * not this session's answer, and the PKCE verifier never leaves here.
 *
 * One at a time, deliberately — a second attempt replaces the first rather than leaving a set of
 * open states to be matched against.
 */
```

Proposed:

```
/**
 * The redirect login, or `mode: 'link'` connect, in progress: an answer whose `state` is not the
 * one this session sent is not this session's answer, and the PKCE verifier never leaves here.
 *
 * One at a time, deliberately — a second attempt replaces the first rather than leaving a set of
 * open states to be matched against.
 */
```

Reason: the flow now also carries a connect, so "the redirect login" no longer says everything the field holds.

## backend/types/fastify.d.ts, `Session.authFlow.mode` / `linkUserId`

**Add** (JSDoc above `mode`):

```
/**
 * Set when the flow starts and never read from the callback's query, so a login cannot be turned
 * into a connect (or back) mid-flight. `linkUserId` is the account a connect binds to; the
 * callback refuses once the session is no longer signed in as it.
 */
```

Reason: this security constraint is enforced only by `api/auth/provider.ts` reading the stored value, and a reader of the type cannot see it.

## backend/models/login.ts, `Login.findOrCreateProviderUser`

**Change** (the `// -> Before anything else:` comment):

Current:

```
// -> Before anything else: a system account (the seeded Guest row) must never be reachable
//    through a provider, and `getByEmail()` has no `isSystem` filter, unlike its siblings.
```

Proposed:

```
// -> Before anything else: a system account (the seeded Guest row) must never be reachable
//    through a provider, and neither `getByProviderLink()` nor `getByEmail()` filters `isSystem`.
```

Reason: `user` can now come from `getByProviderLink()` too, so the comment names only half of the lookup it guards.

**Add** (above the `let user =` lookup):

```
// -> The stored link first: a provider connected through `linkProviderToAccount()` may report an
//    address that belongs to nobody, or to a different account.
```

Reason: the order of the two lookups is load-bearing, and nothing in the code says why the link comes first.

## backend/models/userCredentials.ts, `UserCredentials.linkStrategy`

**Add** (JSDoc above the method):

```
/**
 * The cross-account "identity already linked elsewhere" check runs inside this user's lock but not
 * the other account's, so two accounts connecting the same provider identity at the same moment can
 * both succeed; `users.getByProviderLink()` then resolves to whichever account was created first.
 *
 * @throws `ERR_LINK_NOT_SIGNED_IN`, `ERR_LINK_ALREADY_LINKED` or `ERR_LINK_IDENTITY_IN_USE`
 */
```

Reason: records a known, narrow race and the tie-break it falls back on, which the code cannot show, plus the refusal vocabulary its route maps to redirect codes.

## backend/models/login.ts, `Login.linkProviderToAccount`

**Add** (JSDoc above the method):

```
/**
 * Skips everything a provider login does besides binding the identity: no group sync, no avatar or
 * name fill, and no session. The provider's address need not match the account's.
 *
 * @throws `ERR_EMAIL_NOT_ALLOWED`, `ERR_LINK_NOT_SIGNED_IN`, `ERR_LINK_ALREADY_LINKED` or
 *         `ERR_LINK_IDENTITY_IN_USE`
 */
```

Reason: the deliberate omissions compared with `findOrCreateProviderUser()` are a design decision (Feature #2427) that a reader might otherwise "fix".

## backend/api/auth/provider.ts, authorize route (`sec-fetch-site` check)

**Add** (above the `sec-fetch-site` check):

```
// -> A connect started from another site is how an attacker gets their own provider identity
//    bound to a victim's account. An absent header (older browsers) is allowed.
```

Reason: the header check reads as arbitrary without the account-linking CSRF it defends against.

## backend/models/login.link.test.ts, second `describe`

**Add** (JSDoc above the describe):

```
/**
 * Driven directly, as in `login.providers.test.ts`, with the user lookups stubbed: the account a
 * returning provider login resolves to is what is under test.
 */
```

Reason: explains why a private method is called through a cast.
