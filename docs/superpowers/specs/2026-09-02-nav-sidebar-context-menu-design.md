# Nav sidebar context menu (auto/mixed mode)

Source: OpenProject Issue #2416 ("Research/brainstorm: right-click context menu in the navigation
pane"), Epic #331 "Navigation". Coworker demo feedback, 2026-09-02.

## Problem

The reader-facing nav sidebar (`NavSidebar.vue` / `NavSidebarItem.vue`) has no right-click handling
at all today. When a menu's resolved source is `auto` or `mixed` (`navigation.mode` —
`backend/models/navigation.ts`), its items are generated by walking the real page tree
(`generateFromTree`), so — unlike a hand-authored `static` menu, whose links may point anywhere —
every generated item corresponds to a real page or folder. That makes "create a page/folder/asset
right here" a well-defined action, the same one `PageNewMenu.vue`'s toolbar button already offers,
just with no way to reach it contextually from the tree itself.

`FileManager.vue`'s own tree (`TreeNav.vue`/`TreeNode.vue`) already has a working right-click
context menu (`contextActionList`: `newFolder`/`duplicate`/`rename`/`move`/`del`) — that's the
established mechanism (a `w-menu context-menu` wrapper) this design reuses, not a new one.
`TreeBrowserDialog.vue`'s own tree (shown when saving/renaming/duplicating a page) uses the same
component with just `['newFolder']`, and is the closest existing reference for "right-click →
create here" specifically.

## Scope

**In scope:** creation actions only, matching `PageNewMenu.vue`'s existing action set exactly —
create page (any enabled editor), redirect, import, import batch, new folder, upload asset.

**Out of scope:** rename/move/delete/duplicate on an existing nav-sourced page or folder. Those
already have dedicated flows (the page actions menu, File Manager) — adding them to the nav sidebar
is separate, later work, not part of this Feature.

**Out of scope, flagged as a separate follow-up:** `WMenu`'s `context-menu` mode only opens on the
native `contextmenu` event — there is no long-press-for-touch and no keyboard-only trigger. This is
a **pre-existing gap in `TreeNode.vue`'s own context menu** (File Manager, TreeBrowserDialog), not
something new introduced here. Worth fixing once, for all three context menus at once — not inside
this Feature.

## Design

### 1. Backend: two new fields on generated `NavigationItem`s

`NavigationItem` (`backend/models/navigation.ts`) gains, populated only when `generated: true`
(both folder and page rows) by `generateFromTree`:

- **`path`** — the raw tree path, no locale prefix (e.g. `docs/setup`). Lets the frontend compute a
  creation target without a second round trip. Distinct from the existing `target` field, which is
  locale-prefixed and only ever set on page rows.
- **`folderId`** — the tree-row id of the *containing* folder, `null` at locale root. Needed because
  page creation addresses its target by path (`pageStore.pageCreate({ basePath })`) while folder
  creation addresses its parent by id (`POST /sites/:siteId/tree/folders` — `parentId`). Both
  contracts already exist independently; this isn't inventing a third addressing scheme, just
  surfacing what each one needs.

Both values are already in scope where `generateFromTree` builds each item (`row.id` for the current
row; the parent folder's own `row.id`, threaded through the existing recursive call) — no new query.

### 2. Placement rule

Matches the convention `TreeBrowserDialog.vue`/`TreeNode.vue` already establish (right-click a
folder → act inside it):

| Right-click target | `basePath` (pages/import) | `parentId` (new folder) |
| --- | --- | --- |
| A **folder** item | `item.path` | `item.id` |
| A **page** item (sibling placement) | `dirname(item.path)` | `item.folderId` |
| Empty space in the sidebar | `''` (locale root) | `null` |

The empty-space case is offered only when the resolved menu is `auto`/`mixed` — a `static` menu has
no backing tree to create "into".

### 3. Frontend: reuse `PageNewMenu.vue`, don't reimplement its item list

`PageNewMenu.vue`'s own root element is itself a `<w-menu>` — per `WMenu`'s own contract, it
anchors to whatever DOM element it is nested inside, opening on that element's click by default.
Every existing call site (`HeaderNav.vue`, `HeaderActionsMenu.vue`, `FileManager.vue`) relies on
that click-to-open behavior, so this design adds one new prop rather than wrapping it in a second,
redundant `w-menu`:

- `PageNewMenu.vue` gains a `contextMenu` prop (default `false`), forwarded straight to its own
  root `<w-menu :context-menu="props.contextMenu" ...>`. Every existing call site is unaffected
  (still opens on click); a caller that passes `context-menu` gets right-click-to-open instead —
  the same switch `TreeNode.vue`'s own `w-menu` already uses for its context menu.
- `NavSidebarItem.vue`: a qualifying row (`item.generated && userStore.can('write:pages')`) places,
  as the last child of its own row element — the same position `TreeNode.vue` places its
  `w-menu context-menu` in — a directly right-click-triggered menu:
  ```
  <page-new-menu
    context-menu
    :base-path="basePathFor(item)"
    :hide-asset-btn="!(userStore.can('write:assets') || userStore.can('write:pages'))"
    @new-folder="openFolderDialog(parentIdFor(item))" />
  ```
  Every creation action (editor pick, redirect, import, import batch) is `PageNewMenu`'s existing
  logic, fed a different `basePath` — no new menu markup. `PageNewMenu`'s own `auto-close` already
  dismisses it on any item click, so no extra close-handling is needed. `newFolder` is the one
  event `PageNewMenu` doesn't resolve itself anywhere it's used (matching its existing contract) —
  the row opens `FolderCreateDialog` with the `parentId` from the table above.
- `NavSidebar.vue`: the same `<page-new-menu context-menu .../>`, as the last child of its root
  `<nav>`, for the empty-space case, gated on the resolved menu's mode being `auto`/`mixed`.

### 4. Permission gating

Matches the existing toolbar button exactly: a global "may they create pages/assets anywhere" check
(`userStore.can('write:pages')` / `userStore.can('write:assets')`) decides whether the context menu
is offered at all — not a per-path check. Real per-path enforcement happens server-side at
save/import time, the same as every other `PageNewMenu` call site. No new permission surface.

## Testing

- Backend: `backend/models/navigation.test.ts` — `generateFromTree` (via `getNav`) emits `path` and
  `folderId` correctly for a nested folder/page fixture, and omits both on a `static` menu's
  hand-authored items.
- Frontend: `NavSidebarItem.test.js` — context menu renders only for `generated` items and only when
  `userStore.can('write:pages')`; `basePathFor`/`parentIdFor` resolve correctly for a folder item, a
  page item, and (in `NavSidebar.test.js`) the empty-space/root case.
